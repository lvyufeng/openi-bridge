一、任务整包输出（openi_task_download_output_archive → GET /ai_task/output/download/all）

接口行为（已验证 2026-10-17）：GET /ai_task/output/download/all?id=000000
-> 200，Content-Type: application/octet-stream，回的是 zip 字节流本身，不走
单文件下载那条 307 跳 OBS 签名直链的路（同一个任务上调
/ai_task/output/download 是 404，两条路由形态不同）。

空产物任务是 22 字节的 zip：解开后 namelist 为空，只有 end-of-central-directory
记录，不是错误。这个 22 字节的数字已验证。

原稿此处的实测（待复核）：在 scratch-repo 仓推 zip_train.py（写
metrics.txt 与 ckpt/model.bin 后 upload_output()），开 TRAIN 任务 000000
（GCU / ENFLAME-T20，spec 229）走 WAITING → RUNNING → FAILED（脚本跑完并上传了
产物，任务态是 FAILED 但输出已落），整包下载为 287 字节 zip，成员
ckpt/model.bin（28 字节）与 metrics.txt（10 字节，内容 b'loss=0.01\n'）。
上面那个 22 字节的空包就是拿 000000 对照测的。

顺带把 /ai_task/output 里原本没透出的元数据补进 openi_task_outputs：
is_task_terminal、can_reschedule、can_download。

二、代码仓只读治理面

接口行为（已验证 2026-10-17，对着 scratch-repo 与 OpenModelZoo/ELMo 打过）：

    openi_list_repo_tags(r)          -> 每项含 name / id / commit_sha / commit_url
                                        （mindnlp 实测 14 条）
    openi_list_repo_releases(r)      -> 该仓没发过 release 时为 0 条
    openi_list_repo_labels(r)        -> 该仓没建过标签时为 0 条
    openi_list_repo_collaborators(r) -> 每项含 login / full_name / permissions
    openi_list_repo_stargazers(r)    -> 每项含 login / full_name

注意 permissions 字段在实测样本里是 null（OpenModelZoo/ELMo 的唯一协作者
cqu-tqy），不是原稿写的「全 true」——这个字段平台并不总是填，调用方不要依赖它。

原稿此处的实测（待复核）：对 scratch-repo 调出 tags 1 条、releases 0 条、
labels 9 条（平台默认 bug/enhancement 等）、collaborators 1 条、stargazers 0 条。
其中「labels 有平台默认 9 条」跟 2026-10-17 的观测（几个仓都是 0 条）对不上，
更没有在别的仓复现出来，下一个人若要依赖这个结论需要重新确认。

从 GitHub 同步过来的 mirror 仓，它的 ref 在平台侧是只读的：tag 删不掉也推不动，
但列出来是正常的，所以这几个工具只做读、不做写。

三、账号发现面

接口行为（已验证 2026-10-17，真账号实调）：

    openi_list_my_orgs()                  -> 8 条（username / full_name / description）
    openi_list_starred_repositories()     -> 非空，含别人与组织 owner 的仓
    openi_list_subscribed_repositories()  -> 非空
    openi_search_topics("pytorch")        -> 3 条，每项含 name 与 repo_count
                                             （pytorch -> repo_count 488）
    openi_search_users("<account>")        -> login + full_name

账号维度的仓列表走 GET /user/starred 与 GET /user/subscriptions，返回的是裸数组
而不是 {code, msg, data} 信封；/user/repos 只列自己 owner 的仓（该账号 447 个），
两者互补。搜索结果不是统一的 list：users 在 data 字段下、topics 在 topics 字段下。

原稿此处的数字（待复核）：orgs 2 条、starred 3 条、subscribed 0 条。2026-10-17
实测 orgs 是 8 条，所以这组计数不采信；接口的返回形态以上面为准。
